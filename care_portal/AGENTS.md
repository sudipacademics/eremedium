# Remedium Care backend portal

Staff console for the Remedium Care pain relief & rehabilitation centres: consultations, physiotherapy plans and sessions, lab bookings, billing, pharmacy, inventory, branches, assets and reports. Public URL: https://care.e-remedium.in
It runs on the same Hetzner server as remediumlabs.in (`167.233.108.90`).

## Run

```bash
npm install
CARE_DEV_USER=dev@local npm run api   # API on http://127.0.0.1:8095, no login check, sample data in data/care.db
npm run dev                           # http://127.0.0.1:5183/
npm run build                         # dist/ for the domain root
```

With `CARE_DEV_USER` set, put any `{ "sid": "dev…", "user": "dev@local", "full_name": "…" }` in `localStorage.care_session` to skip the login screen. Without it the API checks every request against the live ERPNext session.

## How it works

- `src/` is the React app. `/care-api` goes to the Node API, `/api` and `/files` proxy to the live labs site (same as the ops portal).
- `server/` is a dependency-free Node 22 API (`node:http` + built-in `node:sqlite`). Data lives in one SQLite file (`CARE_DB`).
- Sign-in uses the HRMS login (`api.authenticate_user`). The API calls `clinical_people_access.get_my_portal_permissions` for each session (cached 60 s) and enforces the **Care Backend** portal permissions per module and level. System Managers get everything.
- **Lab test master** comes from the main ERP (`api.get_lab_test_catalog`, Item group "Lab Tests") into `services` (`category = 'lab'`, `source = 'erp'`, `code` = ERP item code). Import: Test & Lab → Test Catalog → "Import from ERP" (`POST /care-api/services/import-lab`), plus an automatic sync at start-up when never imported and every 24 h (`CARE_LAB_SYNC=0` turns it off). Names, MRP, sample, report time and group follow the ERP; price follows the ERP rate unless `price_override` is set by editing the price; tests dropped from the ERP are set inactive, never deleted. Booking and billing search this list via `GET /care-api/services`.
- **Diagnostics** (X-ray, USG, Doppler, ECG, Echo, TMT, Holter, NCV, EMG, EEG, PFT, audiometry, DEXA…): the master lives in the main ERP as DocType `HEC Diagnostic Test`, each backed by a sales Item in the `Diagnostics` item-group tree (Radiology & Imaging / Cardiology / Neurology / Pulmonology / Other Diagnostics) with its price in the default selling price list (`MRP`). ERP module: `health_ecosystem_core/.../clinical_care_catalog.py` (`get_care_service_catalog` read-only; `save_care_diagnostic_test` needs a session with Care Backend → Diagnostics create/edit or System Manager). The portal's Diagnostic Test Master (`/diagnostics/master`) saves to the ERP through `POST /care-api/diagnostics/tests` (user's own sid) and mirrors the row locally (`services.category = 'diagnostic'`); local create/edit of diagnostic services is refused. Bookings: type `diagnostic`, flow Scheduled → Checked In → In Session → Report Pending → Reported, with findings, reporting doctor and a printable report.
- **Lab bookings and reports follow the partner (collection-centre) workflow.** Remedium Care is the company-owned collection centre `REMEDIUMCARE` (Franchisee Profile, Pulse = FOCO rate by default; switch Franchisee Type to Vector in the ERP for MRP billing; no wallet, no platform invoice). ERP module `health_ecosystem_core/.../clinical_care_lab.py` (shipped via the People add-on store) books through the same Phase 70 save as the Partner portal (`Customer TRF`, channel `Hub Walk-in`, draw plan, barcode, patient payment history) and reads the Phase 123 lifecycle; the Lab Tech portal then accessions, reports and authorises as usual. Endpoints `care_lab_quote / care_lab_book / care_lab_bookings / care_lab_booking / care_lab_payment / care_lab_report` take the user's sid and enforce Care Backend levels (Test & Lab create to book; Billing & Invoice or Test & Lab create to collect; view to track/download). Care side: `server/lab.mjs`, table `lab_bookings` (local index keyed by `trf_id`, refreshed from the ERP whenever the lab screens are opened) and one mirror invoice per booking (`invoices.trf_id`; payments go to the ERP first; cannot be cancelled in Care). Local lab appointments, lab bills from Billing and lab result entry are refused; old clinic lab records stay read-only. UI: `/lab` (bookings + status), `/lab/reports` (authorised PDFs), patient page tab "Lab tests & reports".
- **Branch pharmacy** (`/pharmacy`, `server/pharmacy.mjs`): medicine stock lives in the Operations pharmacy (ERP `clinical_ops_pharmacy.py`, `Ops Med *` DocTypes; each Care branch is an `Ops Med Location` with `care_branch_id`). Care calls the wrapper `clinical_care_pharmacy.py` (add-on store; it only calls the Operations module's functions, never edits it) with the user's sid: board, sellable, ledger, requisition, cancel, receive (delivery confirmation), branch return, dispensed/damaged adjustment, challan PDF, and sale dispense/restock. Access = Care Backend → Pharmacy level + the user's HR Care branches (Operations users keep their Operations access). Pharmacy bills with ERP medicines (`items[].med` = ERP item) are saved, then FEFO-dispensed from the branch under the invoice number ("Care Sale" ledger rows, batches written on the bill); if stock can't be taken the bill is removed; cancelling restocks the same batches. Local `items` with category Medicine are no longer offered in pharmacy billing, and Inventory refuses stock-in and opening stock for them (`MEDICINE_IN` in `api.mjs`): medicines come in only by requisition or an approved outside purchase. **Outside purchases** tab: the branch asks to buy from an outside vendor (`POST /pharmacy/external`), the Operations Manager approves in the Operations portal, then the branch enters the bill (`/pharmacy/external/receive`, within approved qty/price/validity) and the batches join its stock; `/pharmacy/external/cancel` while nothing is bought. Approval, dispatch and central purchases stay in the Operations portal.
- **Care catalogue sync** (`POST /care-api/services/import-care`, plus start-up/daily auto-sync) brings in diagnostics, the ERP `Physiotherapy & Rehabilitation` items and the `Services` consultation item. Sync only hides rows of the categories it syncs.
- **My HR Workspace** (`/my-hr`, shown to every signed-in user) embeds the People HRMS self-service profile, same as the ops and aesthetic consoles. The page answers the frame's `pa-embed-ready` message with the portal session; People only accepts it because `https://care.e-remedium.in` is listed in `EMBED_PARENTS` in `health_web_app/public/people-access.js`.
- **Branch-based access (from HRMS).** HR sets each employee's branches in Portal Access → Care Backend → Branches (`People Portal Access.branches`, JSON ids or `["*"]` = every branch incl. new ones). Empty = the branch of the employee's HRMS Unit / Centre (`Employee.people_unit`, e.g. "Remedium Care - Hasnabad" → branch "Hasnabad"; name match). Staff get one branch; more than one or All needs Care Manager (Manage on any Care module); only HR Manager / System Manager can grant that. HRMS returns the resolved scope as `care_branches` in `get_my_portal_permissions`; `auth.mjs` turns it into `session.branches` (null = all). `server/scope.mjs` runs before every handler: pins `q.branch` to an allowed branch (no "All branches" for restricted logins), returns 404 for records of other branches reached by URL id, 403 for body references (`patient_id`, `invoice_id`, `practitioner_id`…) to other branches, stamps new records with the working branch, trims `/meta` and `/branches`, and keeps branch creation, settings changes, sample-data removal and the activity log to all-branch logins. HR's branch list comes from the public `GET /care-api/branch-directory` (id, name, code, city, active), so new branches appear in HRMS automatically.
- On first start the API seeds the branch, price list and settings, plus sample records marked `demo = 1`. Settings → Sample data removes them (and anything recorded against sample patients). Set `CARE_SEED_DEMO=0` before the first start to skip them.

## Aesthetic session engine (same code, second instance)

The Remedium Aesthetic console (aesthetics.e-remedium.in) uses this engine for **Services → Session Management / Treatment Plans**: treatment plans, packages, custom packages, per-session price, package + session invoices, payment before completion, referral, therapists — identical behaviour to Care's physiotherapy plans.

- Server: `aes-api.service` runs the same `server/server.mjs` with `CARE_FLAVOR=aesthetic` on 127.0.0.1:8096, database `data-aesthetic/aesthetic.db` (backed up on every deploy to `backups/aesthetic-sessions-*.db`). Access comes from Portal Access → **Aesthetic Backend** (Services → plans/sessions/patients/treatments, Invoices → billing, Employees → staff, Branches, Settings; without an access row Aesthetic Manager = manage, Aesthetic Staff = edit). No branch scoping; branches Bongaon / Barasat. Treatments sync daily from `appointments.get_allied_health_services(wing_id="aesthetics")` (category `physiotherapy` internally; plan codes `AT-`, invoice prefix `RA/INV`).
- Frontend: `npm run build:aesthetic` (`.env.aesthetic`, `src/flavor.ts`, `src/components/AestheticEmbed.tsx`) → `dist-aesthetic/`, served at `https://care.e-remedium.in/aes-sessions/` (API `/aes-api/`), frameable only by aesthetics.e-remedium.in (`frame-ancestors`). It is hosted on care.e-remedium.in so the main SPA's service worker on the aesthetics host never intercepts it.
- Console side: add-on `health_web_app/public/aesthetic-sessions.js` (People add-on store, registered in `.deploy/restore_people_addons.py` FILES/TAGS) frames `/services/sessions` and `/services/plans` and hands the console sign-in (`hec_web_session`) to the frame by `postMessage` (`aes-embed-ready` → `aes-embed-session`). `aesthetic-plans.js/.css` are now stubs. The console's Invoices / Payments pages are untouched (still browser-only).
- Deploy both: `npm run build && npm run build:aesthetic`, upload `dist dist-aesthetic server nginx deploy`, run `deploy/install.sh` (restarts care-api and aes-api).
- **Patient feedback (Aesthetic only, `server/feedback.mjs`):** every appointment that becomes Completed/Reported (PATCH `/appointments/:id`) gets one row in `feedback_requests` with a random 32-character link token (only its SHA-256 is stored) and is sent at once through the ERP method `clinical_aesthetic_feedback.aesthetic_feedback_send` (People add-on backend store) as the signed-in staff member: WhatsApp via `send_whatsapp`, then SMS through an MSG91 Flow template set as `aesthetic_feedback_sms_template_id` in site_config. Patients answer at `https://remediumaesthetics.in/feedback/<token>` (no sign-in; public `GET/POST /public/feedback/:token`, rate-limited, CORS for remediumaesthetics.in only); one answer per request (unique `request_id`), links expire after `feedback_link_days` (default 7). Reviews (`reviews`, codes `RV-`) are moderated To Review / Published / Hidden / Flagged and every step is in `review_events`; nothing is deleted. Admin routes `/feedback/*` need Aesthetic Backend → Bookings (or Services for viewing and sending); settings need Bookings manage or Settings edit. Resend/Copy link issue a new token and the old link stops working. Console page: `health_web_app/public/aesthetic-reviews.{js,css}` on `/bookings/reviews`.

## Deploy

- Web root: `/opt/health-ecosystem/care_portal/dist`
- API: `/opt/health-ecosystem/care_portal/server`, systemd `care-api.service` (user `careapi`, port 8095)
- Database: `/opt/health-ecosystem/care_portal/data/care.db` (backed up to `/opt/health-ecosystem/backups/care-*.db` on every deploy)
- Config: `/etc/nginx/sites-available/care.e-remedium.in` (source in `nginx/care.e-remedium.in.conf`)
- Certificate: `/etc/letsencrypt/live/care.e-remedium.in/`
- DNS: `care.e-remedium.in` A to `167.233.108.90`

Update: `npm run build`, upload `dist server nginx deploy` to `/tmp/care_portal/`, then `bash /tmp/care_portal/deploy/install.sh`. The script swaps code, restarts the API, installs nginx (HTTP bootstrap + certbot on first run) and never touches the database.

Portal access for HR lives in `health_ecosystem_core/.../clinical_people_access.py` (`PORTALS["care"]`, roles Care Staff / Care Manager). On the server that module ships through the People add-on store (`/opt/health-ecosystem/people-addons/backend/`, see `AGENTS_CONTEXT.md`).
